# Ronda 2026-08-11 — subtítulos, sesión y el fin de `libranger-jni.so`

> Registro de evidencia de una sesión de depuración. Se documenta cada fallo con **el síntoma**,
> **la causa raíz probada** (no supuesta), **el arreglo** y **cómo volver a verificarlo**.
> Todo lo de aquí se reprodujo antes de tocar una línea de código.
>
> Commits: `390736d` (player + sesión) y `42548e5` (sign_o3 en Python puro). Release: **v1.5.0**.

## Resumen

Seis fallos, tres de ellos invisibles desde el CLI (fallaban del lado del player o del binario
publicado), más la eliminación de la última dependencia nativa del proyecto.

|---|-------|-------|---------|

## 1. VLC nunca cargaba el subtítulo

### Síntoma

Al abrir un capítulo, VLC muestra:

```
Your input can't be opened
VLC is unable to open the MRL 'file:////http%3A//vpnwqk.k9ijj2.com/public/subs/b46ac140-...'
```

### Causa raíz

`_open_in_player` pasaba `--sub-file=http://…srt`. **VLC trata `--sub-file` como ruta de disco**:
`vlc_path2uri()` ve que el string no empieza por `/`, lo toma como ruta *relativa* y le antepone
el CWD. Log del propio VLC con `-vvv`:

```
main input debug: forced subtitle: http://vpnwqk.k9ijj2.com/public/subs/0824…srt
main input debug: looking for a subtitle file in /…/scratchpad/
main input debug: loading spu-es slave: file:///…/scratchpad/http%3A//vpnwqk.k9ijj2.com/…/0824…srt
filesystem stream error: cannot open file /…/scratchpad/http://vpnwqk…srt (No such file or directory)
main input warning: failed to add … as slave
```

Se descartó primero que el problema fuera la URL: `curl` sobre el `.srt` devuelve `HTTP 200`,
22.445 bytes. El subtítulo estaba sano; el que fallaba era VLC.

### Arreglo

`--input-slave`, que sí acepta MRLs y admite varias separadas por `#`.

```python
sub_args.append("--input-slave=" + "#".join(s["url"] for s in subtitles))
```

### Verificación

```bash
/Applications/VLC.app/Contents/MacOS/VLC -I dummy -vvv --no-video --play-and-exit \
  --input-slave="http://…/es.srt#http://…/en.srt" test.wav 2>&1 | grep "loaded .* subtitles"
```

```
subtitle demux debug: detected SubRIP format → loaded 332 subtitles     (es)
subtitle demux debug: detected SubRIP format → loaded 406 subtitles     (en)
```

## 2. `open -a VLC … --args` descarta las banderas

### Síntoma

Dos síntomas que parecían no tener relación: los subtítulos funcionaban "a veces", y **un canal
en vivo mostraba el error de subtítulo de un capítulo** — cuando el vivo no lleva subtítulos.

### Causa raíz

En macOS, `open -a App doc --args …` sólo entrega los argumentos **cuando la app arranca de cero**.
Si ya estaba corriendo, LaunchServices le pasa el documento por AppleEvent y **descarta `--args`
en silencio**.

Probado en vivo: con VLC ya abierto (PID 76603) se lanzó `open -a VLC silent.wav --args
--input-slave=… --marker-probe-test`. Resultado: **no apareció proceso nuevo y los argumentos del
PID 76603 no cambiaron**.

```
--- VLC PIDs ANTES ---   75447 76603
--- VLC PIDs DESPUES --- 75447 76603
76603 …/VLC --http-user-agent=Ranger/4.9.4-17294ac0 --sub-file=http://vpnwqk…srt   ← intacto
```

Consecuencia doble:

1. En la 2ª reproducción se perdían subtítulos **y** el `User-Agent`.
2. El proceso vivo conserva sus opciones globales del lanzamiento anterior y **se las aplica a
   cada ítem nuevo**. Por eso el canal en vivo heredaba el `.srt` del capítulo: el vivo usa el
   mismo `_open_in_player` (`magia.py:1169`) con `subtitles=None`, pero VLC ya traía el
   `--sub-file` viejo cargado en memoria.

> Detalle que agrava el caso: bastaba con que estuviera vivo el *helper headless* del proxy de TV
> en vivo (`--intf dummy --no-video`) para que `open` considerara "VLC ya corre" y tirara las banderas.

### Arreglo

En macOS se lanza el binario del bundle, no `open`. Un proceso por reproducción, sin herencia
entre ítems. Si el bundle no está donde se espera, cae a `open -na` (con `-n`, instancia nueva).

```python
vlc_bin = "/Applications/VLC.app/Contents/MacOS/VLC"
cmd = [vlc_bin, url, "--http-user-agent=…"] + sub_args
```

IINA arrastraba el mismo defecto y recibió el mismo tratamiento vía `iina-cli`.
**No verificado empíricamente**: IINA no estaba instalada en la máquina de pruebas.
mpv se dejó con `--sub-file` porque, a diferencia de VLC, resuelve URLs por su capa de streams
(tampoco verificado en vivo: mpv no estaba instalado).

### Verificación

```bash
python3 -c "
import subprocess; cap=[]
subprocess.Popen = lambda c,*a,**k: cap.append(c)
import magia
magia._open_in_player('vlc','http://cdn/x.mp4','a','l',subtitles=SUBS); print(cap[-1])
magia._open_in_player('vlc','http://127.0.0.1:41389/x.m3u8','',''); print(cap[-1])"
```

El comando del capítulo lleva `--input-slave` con ambos idiomas; el del vivo va limpio.

## 3. La sesión moría con el CLI idle

### Síntoma

Dejando el CLI abierto un rato largo sin usarlo, la búsqueda dejaba de funcionar hasta cerrar
y volver a abrir.

### Causa raíz

Se provocó a propósito con un token inválido:

```
search    → {"_error": "aaa100028", "_msg": "未登录！", "_path": "v3/searchByName"}
play_vod  → {"_error": "aaa100028", "_msg": "未登录！", "_path": "v10/startPlayVOD"}
```

**`aaa100028` = "no has iniciado sesión"**, y es el código más frecuente del APK decompilado
(18 apariciones). La app **no refresca el token ni tiene heartbeat de sesión**: marca la sesión
como inválida y abre el diálogo de login.

- `com/module/basemvp/AbstractActivityC2036a.java:308` — ante `aaa100028`/`aaa100027` llama a
  `m0.m6095V(true)` y muestra el fragment de login.
- `ac/f1.java:130` — mismo tratamiento.
- Los únicos `heartbeat` del APK son de la librería de red de Alibaba (`anet/channel/heartbeat/*`),
  a nivel TCP: no tienen que ver con la sesión del portal.

### Arreglo

`IPTVClient.call()` detecta `aaa100027`/`aaa100028`, re-mintea la sesión **por la misma vía con
que se obtuvo** y reintenta una vez:

- `account` → `v8/login` con las credenciales guardadas en el login original.
- `device` → `v8/active`.
- `manual` (token capturado a mano vía `use_account`) → **no se renueva a propósito**: activar
  ahí degradaría una sesión de cuenta a tier free en silencio.

Las rutas que establecen o cierran sesión quedan excluidas del reintento
(`v8/active`, `v8/login`, `v5/loginOut`, `v3/snToken`); en `v3/snToken` reintentar sería dañino
porque corre con el device a medio limpiar.

### Verificación

```
=== sesion device, token corrompido a mano ===
busqueda tras token muerto -> resultados: 19 | _error: None
token renovado? True

=== capitulo real tras matar el token ===
err: None | streams: 1 | subs: [('es', …), ('en', …)] | token renovado: True

=== sesion 'manual' NO se degrada a free ===
resultado: aaa100028 | token intacto: True
```

## 4. El Content-Auth del CDN también caducaba

### Síntoma

Descubierto mientras se hacía el smoke test del CLI, no reportado por el usuario:

```
> CDN listo -- auth valido por 4.0 horas
```

### Causa raíz

`cdn_base` / `cf_auth` se capturan **una sola vez al arrancar** (`magia.py`, tras el login) y se
pasan **por valor** por todo el árbol de menús. Los caminos de descarga refrescan ante un 401,
pero los de **streaming** y los de **mostrar links** usaban siempre el auth del arranque.

Resultado: con el CLI abierto más de ~4 h, al reproducir se le entregaba al player un
Content-Auth vencido. El fallo ocurría **dentro de VLC**, así que el CLI no mostraba ningún error.

### Arreglo

`fresh_cf_auth()` renueva en el punto de uso si el auth vence dentro de 5 minutos. El `expired=`
viene en el propio querystring. Si no hay campo `expired` no se juzga y se deja como está (siguen
valiendo los reintentos por 401 de la ruta de descarga).

### Verificación

```
auth real -> expired en 4.0 h
caso A: auth VIGENTE            → sin cambios: True
caso B: auth VENCIDO            → renovado: True, nuevo expired en 4.0 h
caso C: sin campo expired       → sin cambios: True
```

## 6. `libranger-jni.so` y Unicorn, fuera

### El punto de partida

La TV en vivo era lo único que seguía dependiendo de código nativo. `sign_o3` firma cada segmento
`.ts` con un MD5 modificado, y ese MD5 se resolvía **emulando con Unicorn** la función `0x529178`
de `libranger-jni.so`: un binario propietario de 7,9 MB que además está **gitignoreado**, así que
en un clon limpio el vivo no arrancaba.

De `SIGN_O3_CRACK.md` se sabía casi todo: IV, K, shifts y funciones F estándar; el *message
schedule* de la 1ª vuelta tweakeado; y **4 rondas anómalas (42, 45, 54, 62)** cuyo cómputo no
encajaba con ninguna de las 4 F estándar. Eso era lo que faltaba.

### Cómo se derivó

La función emulada ejecuta **exactamente un `ror` por ronda**, 64 en total. Hookeando cada uno con
`UC_HOOK_CODE` y leyendo el registro fuente *antes* de ejecutar se obtiene el valor pre-rotación:

```
f_i = a + F(b,c,d) + K[i] + M[g]
```

Los `rotl` equivalentes salieron `[7,12,17,22]×4, [5,9,14,20]×4, …` — el shift schedule estándar
de MD5, confirmando una captura por ronda y en orden.

Con el estado reconstruido ronda a ronda se despeja `(F, g)` probando las 4 funciones estándar por
las 16 palabras del bloque y cruzando varias muestras aleatorias. **60 de 64 rondas** quedaron
determinadas de inmediato, y el feed-forward resultó Davies-Meyer estándar.

Para las 4 restantes se planteó otra pregunta: en vez de buscar una `F` distinta, exigir que

```
X − F(b,c,d) − M[g]
```

fuese **constante entre muestras**. Si lo es, la ronda es estándar salvo por la constante, y esa
diferencia es `K'[i] − K[i]`. Lo fue, con la `F` y la palabra estándar en las cuatro.

### El tweak completo

Sólo dos cosas. Todo lo demás —IV, F/G/H/I, shifts, padding little-endian, Davies-Meyer— es MD5 de manual.

1. Message schedule de la 1ª vuelta: `[10,11,12,13,14,15,6,7,8,9,0,1,2,3,4,5]`. Vueltas 2–4 estándar.
2. Cuatro constantes K cambiadas, con pinta de **erratas de transcripción** del MD5 original:

   | ronda | K estándar | K real     | nota |
   |-------|------------|------------|------|
   | 42    | `d4ef3085` | `d46f3085` | un bit |
   | 45    | `e6db99e5` | `e6bd99e5` | `db` → `bd` transpuesto |
   | 54    | `ffeff47d` | `ffecc47d` | |
   | 62    | `2ad7d2bb` | `2da7d2bb` | `ad` → `da` transpuesto |

### Verificación

`test_tweaked_md5.py` se escribió **antes** que la implementación, y cada test se vio fallar por
el motivo correcto antes de implementarlo.

- `compress` idéntica al `.so` en 200 bloques aleatorios y en casos borde.
- `digest_hex` idéntica en mensajes de 0–300 bytes, incluidas las fronteras de padding (55/56, 63/64).
- Los 5 vectores capturados de la app en vivo: **5/5**.
- Un test corre `sign_o3` en un subproceso con `unicorn` ausente y exige la firma correcta.
- **Prueba de fuego** con el `.so` movido de sitio y `unicorn` bloqueado:

```
unicorn disponible: False
.so visible para el codigo: False
canales: 1000
canal: LGVIP La Gala -> cyx_50fdcc0817d61_720p
GET playlist -> 200, 6 segmentos
GET segmento .ts -> 200 | primeros bytes: 4740003f   (0x47 = sync byte de MPEG-TS)
```

La emulación con Unicorn **se conserva** en `sign_o3.TweakedMD5` como oráculo de los tests, con
import perezoso para no imponerla en runtime.

## 7. Efecto colateral: los binarios publicados estaban rotos

Al preparar el release se detectó algo que no se buscaba.

`.github/workflows/release.yml` instala `pyinstaller pycryptodome requests rich InquirerPy` —
**nunca instaló `unicorn`**, y `magia.spec` tampoco lo declara en `hiddenimports`. Pero la cadena
de imports era:

```
magia.py:39  from live_stream import LiveSession, LiveProxy
live_stream.py:23  from sign_o3 import sign_o3, now_moment_ms
sign_o3.py:29      from unicorn import Uc, …          ← a nivel de módulo, incondicional
```

Comprobado sobre el árbol anterior al arreglo (`git worktree` en `HEAD~1`, con `unicorn` bloqueado):

```
RESULTADO: CRASH -> ModuleNotFoundError import of unicorn halted
```

O sea que **ningún binario publicado (v1.1.0 … v1.4.6) podía siquiera arrancar**: sin `unicorn` en
el entorno de build, PyInstaller no podía empaquetarlo, y el ejecutable moría en el import inicial.
Sólo funcionaba corriendo desde el fuente en una máquina que tuviera `unicorn` instalado a mano.

Al volver Python-puro el camino de firma, el import desapareció y los binarios arrancan. **v1.5.0
es la primera release realmente utilizable.**

## 8. Canales que el CDN rechaza, anunciados como si funcionaran

### Síntoma

Al abrir un canal en vivo, VLC muestra:

```
Your input can't be opened
VLC is unable to open the MRL 'http://127.0.0.1:50189/play.m3u8'
```

Parece que fallara el proxy local — de hecho la URL es de `127.0.0.1` — pero el proxy estaba bien.

### Causa raíz

**No todos los canales listados están autorizados.** Probando el mismo mecanismo sobre varios:

```
WIN Sports HD          playlist HTTP 401   172b
WIN Sports COL HD      playlist HTTP 200  1496b
WIN Sports+ COL HD     playlist HTTP 200  1519b
LGVIP La Gala          playlist HTTP 200  1105b
```

El cuerpo del 401 es un `401 Authorization Required` de nginx: el edge del CDN rechaza ese canal
concreto. La API lo lista igual, así que `resolve_live_cfl` funciona y el proxy arranca sin
problemas; el rechazo llega recién al pedir el playlist.

El proxy reenvía el status del CDN tal cual (`self.send_error(r.status_code)`), y VLC lo traduce a
su mensaje genérico con la URL local. Mientras tanto **el CLI ya había dicho `Streaming: …`**, con
lo cual toda la evidencia apuntaba al lugar equivocado.

Conviene subrayarlo porque despista: *no es un fallo del proxy ni del `sign_o3`*. Se verificó que
el proxy sirve el playlist correctamente (`HTTP 200`, m3u8 válido) y que VLC lo abre y empieza a
pedir segmentos (`successfully opened` en el log) para los canales autorizados.

### Arreglo

`live_playlist_error()` prueba el playlist **antes** de anunciar nada y antes de abrir el player.
Si el CDN lo rechaza, se apaga el proxy, se lo saca de `_ACTIVE_LIVE_PROXIES` y se muestra el
motivo real. El 401 tiene mensaje propio porque es el caso frecuente.

### Verificación

```
--- canal que daba 401: WIN Sports HD ---
  x  No se puede reproducir WIN Sports HD: HTTP 401: el CDN no autoriza este canal.
     Suele ser un canal premium que tu plan actual no incluye -- probá con otro.
     player lanzado: False

--- canal que funciona: LGVIP La Gala ---
  >  Streaming: LGVIP La Gala
     player lanzado: True

proxies vivos al final: 1   (solo el del canal bueno)
```

`test_live_probe.py` cubre los cuatro escenarios (200, 401, 502 y proxy caído) levantando
servidores HTTP reales, sin mocks.

## 9. El segundo canal en vivo no abría hasta reiniciar el CLI

### Síntoma

El primer canal reproduce bien. Se cierra VLC, se elige otro canal, y ya no abre. Cerrando y
reabriendo el CLI vuelve a funcionar.

```
x  No se pudo resolver el canal en vivo: play_live sin liveAddressList:
   {'_error': 'aaa100083', '_msg': '您的账号已经在其他设备登录', '_path': 'v4/startPlayLive'}
```

`aaa100083` = *"tu cuenta ya inició sesión en otro dispositivo"*.

### Descartado primero: no es VLC

La sospecha inicial era que relanzar VLC por el binario del bundle (cambio del punto 2) fallara la
segunda vez. **Falso**: se lanzaron tres VLC simultáneos por esa vía y los tres siguieron vivos a
los 5 s. También se descartó que `stream_live` dejara de lanzar el player — cuatro canales
seguidos lo lanzan sin problema.

### Causa raíz

Tres intentos de reproducción **fallaron** y conviene anotarlos, porque descartan explicaciones
plausibles: llamadas seguidas a `play_live` (4/4 OK), streaming corto de 3 segmentos (OK), y una
re-autenticación forzada seguida de `play_live` (OK). Ninguno lo provoca.

Lo que sí lo provoca es **streaming sostenido**:

```
tras ~30s de streaming (10 segmentos)  -> otro canal: OK
tras ~60s de streaming (17 segmentos)  -> otro canal: OK
tras ~90s de streaming (23 segmentos)  -> otro canal: OK
tras ~120s de streaming (29 segmentos) -> otro canal: FALLA aaa100083
cerrando el "VLC" y reintentando       -> FALLA aaa100083
apagando tambien el proxy              -> FALLA aaa100083
```

Pasado un par de minutos de reproducción el servidor marca el device como *transmitiendo*, y ese
estado **no se limpia** al dejar de pedir segmentos ni al apagar el proxy. Nada le avisa al portal
que se dejó de reproducir. Sólo una sesión nueva lo destraba — que es exactamente lo que hacía
reiniciar el CLI.

### Arreglo

`aaa100083` pasa a la lista de códigos recuperables, con re-activación del device y reintento:
es lo mismo que hace la app, que lo mete en la misma rama de sesión inválida que `aaa100027/28`
(`ac/f1.java:142`).

**Sólo en modo device/free.** Con una cuenta real, re-loguear expulsaría al otro dispositivo y
armaría un ping-pong, así que ahí se devuelve el error. `test_session_recovery.py` fija esa
distinción.

Además, `describe_live_error()` traduce el código: el usuario ya no ve un dict con texto en chino.

### Verificación

Con el arreglo, tras 150 s de streaming real (35 segmentos):

```
=== intentando otro canal (deberia auto-recuperarse) ===
   RESULTADO: OK -> LGVIP En Vivo 1 resolvio (host=niguof.vynbszicd.com)
   token cambio (hubo re-activacion): True
```

La llamada verificada es `resolve_live_cfl`, que es exactamente la que hace `stream_live`.

## Cómo re-verificar todo

```bash
python3 -m unittest test_tweaked_md5 -v     # 6 tests: equivalencia con el .so + vectores dorados
python3 -m unittest test_live_probe -v      # 7 tests: 200/401/502/proxy caido + mensajes
```

Para la suite de equivalencia hace falta `libranger-jni.so` + `unicorn`, que son **sólo de
desarrollo**: son el oráculo. Sin ellos los tests se saltan solos.

> **Conservá tu copia del `.so`.** No hace falta para usar el CLI, pero es lo único que puede
> avisarte si Magis TV cambia el algoritmo de firma. Sin él, esos tests se saltan en silencio.
